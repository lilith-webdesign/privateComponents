# 水利信息化移动端：全局交互规范与分角色 UI 设计哲学

> 调研报告 · 2026-07-10（按业务附表校正）

## 1. 全局交互需求（全角色共用规范）

本章是**所有角色的 UI 底盘**。分角色章节只允许在此之上做优先级、密度与流程摩擦的调整，不允许另起一套互不相干的视觉语言。

### 1.1 设计目标（三条总纲）

| 总纲 | 含义 | 可观察结果 |
|------|------|------------|
| **核心数据最小可读** | 用最少字段让用户读懂业务含义 | 3 秒内知「对象是谁、现在怎样、是否要我处理」 |
| **轻采集** | 能自动的不手填，手填只留给判断 | 扫码/定位/拍照回填；键盘字段显著减少 |
| **可触达、可闭环** | 消息与入口必须落到可处理对象 | 点通知进告警/工单详情，而不是空白首页 |

### 1.2 全局布局规范

#### 1.2.1 页面骨架（稳定三区）

```text
┌─────────────────────────┐
│ 上下文区（对象/任务/网络） │  ← 始终知道「我在处理什么」
├─────────────────────────┤
│                         │
│ 内容区（列表/详情/地图）  │  ← 主阅读与比较
│                         │
├─────────────────────────┤
│ 主操作区（底部拇指区）    │  ← 唯一视觉主按钮优先放这
└─────────────────────────┘
```

**规范条文：**

1. **禁止**把 PC 多栏后台整体缩小塞进手机。  
2. 手机默认**单列任务流**；宽屏/折叠屏才升级列表+详情。  
3. 加载与刷新时，标题区与底部主操作位置**不得跳动**（骨架与终态同构）。  
4. 内容区滚动，上下文与主操作可固定；固定栏必须留安全区。  
5. 一屏**最多一个**视觉主按钮；次要操作降级为文本/描边/更多。

#### 1.2.2 信息架构默认值

| 场景 | 默认 IA | 说明 |
|------|---------|------|
| 有待办/告警职责的角色 | **任务工作台** | 先答「现在处理什么」 |
| 公众与轻查询 | **服务入口 + 个人事务** | 查询/报修/缴费路径短 |
| 管理与行政 | 工作台 + 二级「全部业务」 | 门户不得压过待办 |

模块九宫格**不得**作为有现场职责角色的默认首页。

### 1.3 List / Card 设计规范

#### 1.3.1 列表的职责

列表只负责：**识别、比较、进入下一步**。  
不负责：塞满全部字段、嵌完整图表、堆多个同权按钮。

**列表行 / 任务卡最小结构：**

```text
[状态]  标题（对象 + 事件）
        2～4 个关键元信息（时限 · 位置 · 责任 · 更新时间）
                              [下一步/标签]
```

**条文：**

1. 标题必须业务可读（如「东干渠 2# 闸门 · 反馈异常」），禁止纯编号当主标题。  
2. 状态用**文案 + 色彩**，禁止只靠颜色。  
3. 一行主动作最多一个；其余进详情或更多。  
4. 危险操作（删除、关闭告警、下发控制）**不得**与主前进动作贴邻同权。  
5. 空列表要区分：真无数据 / 筛选无结果 / 无权限 / 离线不可用。

#### 1.3.2 详情卡与分组

详情才展开完整阅读：基础信息、监测、附件、时间线、关联工单。  
高级与低频操作收入「更多」，避免详情页变成按钮墙。

### 1.4 按钮与操作位置

| 操作类型 | 位置 | 形态 |
|----------|------|------|
| 当前阶段唯一主路径 | 底部通栏 / 底部操作岛 | 实心主色，高度建议 48–56 |
| 次要路径 | 主按钮上方或文本链 | 描边/文字 |
| 危险操作 | 远离主按钮，或二次确认页 | 警告色，不与主提交并排同权 |
| 现场扫码/定位/拍照 | 表单内大热区或靠近拇指区 | 明确标签，不靠纯图标 |
| 仅管理/配置 | 右上更多或二级页 | 不进现场主路径 |

**拇指区原则：** 高频与现场操作优先屏幕下半区；顶部图标不得作为**唯一**核心入口。

### 1.5 数据如何展示（全局「可信最小集」）

目标：**最小字段，最大业务信息量**——不是最少像素，而是最少认知负担。

#### 1.5.1 核心指标卡（任何角色看到「一个数」时）

```text
对象名称（测站/设施）
主值 + 单位
质量状态：正常 / 超限 / 离线 / 估算 / 过期
更新时间 · 来源（遥测/人工/计算）
（可选）阈值或对比
```

**禁止：** 只有绿色大数字 `28.46`，无单位、无对象、无时间。

#### 1.5.2 列表中的数据

列表里的数必须自带单位或状态词，例如：`28.46 m · 2 分钟前 · 遥测正常`。  
过期数据**不得**使用「一切正常」的成功绿色。

#### 1.5.3 图表（小屏）

最小要素：对象、指标名、时间范围、单位、阈值说明、当前点。  
复杂分析进二级或桌面；移动端优先「结论 + 关键点」，不是大屏搬迁。

#### 1.5.4 状态与过程数据

| 业务真实阶段 | UI 必须表达 | 禁止表达 |
|--------------|-------------|----------|
| 仅请求发出 | 已发送 / 处理中 | 「设备已成功」 |
| 平台受理 | 已受理 | 跳过阶段 |
| 设备回执 | 已回执 + 结果 | 用接口 200 代替回执 |
| 超时 | **结果未知** + 可查询/重试策略 | 武断「失败/成功」 |
| 仅本地保存 | 已存本机 · 待同步 | 「提交成功」 |

### 1.6 轻采集（全局）

能自动则自动，且**可核验、可修改**：

1. 人员、时间、任务号、设施编码：优先自动带入。  
2. 扫码 / 定位 / 拍照 / 语音：作为主采集入口，键盘是补充。  
3. 回填字段旁显示来源（扫码识别 / GPS），允许纠正。  
4. 附件失败：行内状态 + 单项重试，不整单作废。  
5. 长表单：自动草稿 + 可见保存时间。

### 1.7 触达（全局）

1. 通知/订阅消息/推送必须带**对象类型 + ID** 深链。  
2. 落地页是可处理详情，不是营销首页。  
3. 触达文案含：等级或紧急度、对象、建议动作。  
4. 已失效对象：明确「已关闭/已撤销」+ 返回列表。  
5. Toast 只用于短暂可知结果；**不承担告警生命周期**。

### 1.8 反馈分层（全局）

| 层级 | 载体 | 用途 |
|------|------|------|
| 字段 | 行内错误 | 校验 |
| 对象局部 | 行状态 / 附件条 | 单点失败 |
| 页面 | 顶栏 Banner | 离线、过期、只读 |
| 高风险 | 全页摘要 / 确认流 | 控制、不可逆操作 |
| 短暂 | Toast / Snackbar | 「已加入同步队列」等弱结论 |

### 1.9 离线与同步（全局底线）

1. 离线可查看已缓存任务与草稿，可继续轻采集。  
2. 状态词统一：仅本地 / 待同步 / 同步中 / 已确认 / 冲突 / 失败可重试。  
3. **生产控制类指令禁止离线排队。**  
4. 冲突：展示差异，禁止静默最后写入覆盖。

### 1.10 双端共性（写在全局，细节见第 4 章）

- **业务语义两端一致**（状态词、对象字段）。  
- **交互深度可分轨**（能力不足则降级为只读/转审批/引导 App）。  
- 演示可用 Material / Varlet 表达正确侧；生产小程序按语义映射组件，不绑定唯一库。

## 2. 业务附表：角色 × 权限 × 数据视野

以下为系统权威业务输入。**UI 设计必须由此表推导，不得反过来用界面菜单定义角色。**

| 角色名称 | 职责概述 | 核心权限 | 数据视野 |
|----------|----------|----------|----------|
| **管水员** | 管辖区域内水利设施的巡检查看、日常养护与状态上报 | 巡检任务查看与执行、设施状态录入、异常拍照上报、历史记录查询 | 管辖片区内的设施台账、巡检历史、实时监测数据、告警信息 |
| **工程人员** | 水利设施日常维修、抢修调度与施工管理 | 维修工单接收与处理、物资申领、施工记录填报、验收申请提交 | 设施维修历史、备品备件库存、工单进度跟踪、施工质量档案 |
| **调度员** | 县域水资源统筹调度、应急响应与运行监控 | 全域监测查看、调度指令下发、应急预案启动、水位/流量远程调控 | 县域全域实时监测、历史调度记录、流域关联分析、气象预报 |
| **行政人员** | 水务行政审批、督查督办与政策管理 | 审批流程处理、督查任务下发、公文流转、统计报表查看与导出 | 审批业务数据、督查整改进度、部门效能统计、政策法规库 |
| **公众用户** | 县域用水居民、企业等普通公众 | 用水信息查询、在线报修/投诉、水费缴纳、政策资讯、应急预警接收 | 个人用水记录、服务进度、公告通知、服务网点 |

### 2.1 角色与全局规范的关系

| 角色 | 更吃重的全局条款 | 相对全局的「加重」 |
|------|------------------|-------------------|
| 管水员 | 布局下半区、轻采集、离线、List 任务卡、地图 | 现场密度、地图任务化 |
| 工程人员 | 数据可信最小集、工单卡、附件、时间线 | 责任链与来源强化 |
| 调度员 | 过程反馈、高风险协议、指标可信、Toast 边界 | 控制摩擦与全域态势 |
| 行政人员 | 列表分层、审批摘要、导出与只读 | 依据完备、少现场操作 |
| 公众用户 | 触达、短路径、轻表单 | 极简、低概念、强引导 |

## 3. 分角色：业务决定的交互与 UI 设计哲学

每一节结构固定：

1. 业务再述（权限与视野）  
2. 环境与约束  
3. **设计哲学（一句话）**  
4. 首页与信息架构  
5. 关键界面模式（List/Card/按钮/数据）  
6. 平台建议  
7. 验收观察点  

---

### 3.1 管水员

#### 业务

- **权限：** 巡检执行、设施状态录入、异常拍照上报、历史查询。  
- **视野：** 片区台账、巡检历史、实时监测、告警（管辖范围内）。

#### 环境与约束

单手握持多、弱网多、户外强光/雨天常见；移动中操作；地图是业务本身的一部分（去哪、巡哪、是否到位）。

#### 设计哲学

> **下半屏完成主操作，地图托住空间任务，能自动填的绝不手填，断网也能把记录留在本机。**

#### 首页与 IA

- 默认：**今日巡检任务雷达**（待巡 / 进行中 / 异常 / 待同步）。  
- 次级：片区设施、告警（与我相关）、历史。  
- 不做全域调度大屏，不做行政审批入口。

#### 关键 UI 模式

| 模式 | 规范要点 |
|------|----------|
| 任务 List/Card | 标题=设施+任务类型；元信息=时限、距离/位置、状态；主按钮「开始/继续」 |
| 操作区 | **下半屏集中**：开始检查、扫码、拍照、定位、提交草稿 |
| 地图 | 任务上下文：点位、路线、当前位置；列表⇄地图同一任务切换，不是独立 GIS 展览 |
| 表单 | 扫码识别设施后自动带出台账字段；人工只填异常描述与必要选项 |
| 离线 | 顶栏持续显示网络/待同步数；本地暂存队列可点开逐项重试 |
| 数据 | 监测以「当前值+时间+是否超限」轻量出现，服务巡检判断，不做复杂分析 |

#### 平台

- 小程序：轻巡检、上报、消息触达。  
- Hybrid：强离线、轨迹/到位、大批量附件、稳定定位。

#### 验收点

- 单手可完成「打开任务 → 扫码/拍照 → 暂存」。  
- 断网填写不丢；恢复后能区分仅本地与已确认。  
- 地图与列表切换不丢当前任务。

### 3.2 工程人员

#### 业务

- **权限：** 维修工单处理、物资申领、施工记录、验收申请。  
- **视野：** 维修历史、备件库存、工单进度、质量档案。

#### 环境与约束

现场维修与室内填报交替；必须快速搞清「谁的单、修过什么、依据何在」；误填影响验收与追责。

#### 设计哲学

> **一切操作可追溯：时间、责任人、来源一眼可定位；工单推进清晰，数据像档案而不是聊天记录。**

#### 首页与 IA

- 默认：**我的工单**（待接/处理中/待验收）。  
- 次级：物资、施工记录入口、历史档案。  
- 强调进度与截止，弱化全域水文分析。

#### 关键 UI 模式

| 模式 | 规范要点 |
|------|----------|
| 工单 Card | 设施、故障摘要、紧急度、责任人、截止时间、当前节点 |
| 可信条 | 任何关键记录展示 **操作者 · 时间 · 来源（现场填报/系统生成/转派）** |
| 维修历史 | 时间线：何时何人做了什么，可展开附件与验收意见 |
| 表单 | 分组：故障现象 / 处置措施 / 物资 / 验收材料；草稿自动存 |
| 数据 | 库存与进度用「状态词+数量+更新时间」；禁止无来源数字 |
| 按钮 | 主操作随节点变：接单 → 开始处置 → 提交验收；危险「关闭/作废」隔离 |

#### 平台

- 小程序可接单、进度同步、轻量填报。  
- 复杂施工记录、大附件、签章类走 Hybrid 或完整表单页。

#### 验收点

- 打开任一历史项，3 秒内找到责任人与时间。  
- 工单阶段与主按钮文案一致，无「万能提交」。  
- 验收材料缺失时阻断并定位到字段/附件。

---

### 3.3 调度员

#### 业务

- **权限：** 全域监测查看、调度指令下发、应急预案、水位/流量远程调控。  
- **视野：** 县域全域实时监测、历史调度、流域关联、气象。

#### 环境与约束

高后果；需要全域态势但手机不是大屏；指令必须可信、可回执、可审计；误操作成本极高。

#### 设计哲学

> **先看清再动手：只读实时态 → 摘要 → 身份复核 → 分阶段反馈 → 审计时间线；成功必须同时看到过程反馈与实时数据变化。**

#### 首页与 IA

- 默认：**态势摘要 + 待处理调度/告警**（不是巡检清单）。  
- 结构：关键指标条 → 异常对象 → 进行中的指令。  
- 控制入口必须从对象详情进入，禁止列表上的「一键开闸」。

#### 关键 UI 模式

| 模式 | 规范要点 |
|------|----------|
| 全域数据 | 卡片化 KPI：对象、值、单位、质量、时间；下钻到对象 |
| 指令前 | **只读实时态**（当前开度/水位/在线）+ 数据时间 |
| 摘要页 | 固定展示：**目标、影响范围、动作、执行对象、数据时戳** |
| 复核 | 身份/权限确认；平台能力不足则转审批，不假装已下发 |
| 阶段反馈 | 已校验 → 已下发 → 执行中 → 已回执 / 超时未知 |
| 成功可信 | **阶段成功提示（可用 Toast/Snackbar）必须结合影响对象的实时数据变化**（如目标开度与反馈开度、水位趋势点更新）；禁止单独 Toast「调度成功」 |
| 审计 | 详情时间线：谁、何时、何参数、何回执 |
| 按钮 | 主按钮文案跟阶段走（确认摘要 / 复核并下发 / 查看回执）；危险动作高摩擦 |

#### 成功反馈的特别规范（调度员）

```text
错误：Toast「调度成功」→ 结束
正确：
  1) 过程条进入「已回执」或明确阶段
  2) 同屏实时数据刷新（反馈值、更新时间、质量态）
  3) 短提示仅作辅助：「指令已回执，反馈开度 45%」
  4) 若回执超时：显示「结果未知」，保留查询与禁止重复连点策略
```

#### 平台

- **高风险调控以 Hybrid + 安全通道为主。**  
- 小程序：监测、告警、审批协同；无安全能力时不提供直控。

#### 验收点

- 无摘要、无实时态，无法触达下发。  
- 成功态同时具备过程阶段与数据变化。  
- 审计可回放参数与回执。

---

### 3.4 行政人员

#### 业务

- **权限：** 审批、督查下发、公文流转、报表查看导出。  
- **视野：** 审批数据、整改进度、效能统计、政策法规。

#### 环境与约束

碎片时间决策；少现场操作；要的是依据完备与流程清晰，不是地图点检。

#### 设计哲学

> **依据先行、动作简单：先看清批什么、依据是什么，再一键通过/驳回/补件；统计只读优先。**

#### 首页与 IA

- 默认：**待我审批 / 督查待办**。  
- 次级：流转中、统计、法规库。  
- 不做闸控、不做片区巡检地图主路径。

#### 关键 UI 模式

| 模式 | 规范要点 |
|------|----------|
| 审批 Card | 事项标题、来源部门、时限、紧急度、关键结论摘要 |
| 详情 | 分层：申请摘要 → 附件/依据 → 历史意见 → 操作 |
| 数据 | 报表以结论卡+关键指标；导出明确范围与时间 |
| 按钮 | 通过 / 驳回 / 退回补件；驳回必须填原因 |
| 触达 | 待办消息直达审批单 |

#### 平台

- 小程序非常适合待办触达与轻审批。  
- 复杂公文与大批量导出可降级到 Web/桌面。

#### 验收点

- 审批可不进无关业务模块。  
- 无依据时不能「盲批」（关键附件缺失有提示）。  
- 督办进度状态可读、可催办。

---

### 3.5 公众用户

#### 业务

- **权限：** 用水查询、报修/投诉、缴费、资讯、应急预警接收。  
- **视野：** 个人用水、服务进度、公告、网点。

#### 环境与约束

非专业用户；低频；概念要少；应急预警要可达但不可吓成无法理解。

#### 设计哲学

> **短路径、低概念、强进度：查得到、报得了、看得到办到哪；预警能看懂、能知道怎么办。**

#### 首页与 IA

- 默认：常用服务（缴费、报修、查询）+ 公告/预警条。  
- 个人中心：我的工单进度、用水记录。  
- 不暴露内部调度、工单池、设施台账。

#### 关键 UI 模式

| 模式 | 规范要点 |
|------|----------|
| 服务入口 | 大卡片少即是多，文案生活化 |
| 报修单 | 极简表单 + 拍照；自动带联系方式；进度时间轴 |
| 数据 | 个人用水：周期、量、费用，避免内部测点编码 |
| 预警 | 等级文案清晰 + 建议行动；深链到说明页 |
| 按钮 | 主按钮「提交报修/去缴费」；少次要操作 |

#### 平台

- **以小程序为主**（触达、登录便利）。  
- 一般不需要 Hybrid。

#### 验收点

- 首次用户不经培训完成报修。  
- 进度状态生活语言（已受理/处理中/已完成）。  
- 看不到内部角色数据视野。

## 5. 双交付平台：如何承载上述 UI（不改变业务）

| 业务能力 | 小程序 | Hybrid | 对 UI 规范的影响 |
|----------|--------|--------|------------------|
| 触达 | 强 | 强 | 深链规范全局生效 |
| 管水员轻巡检 | 适合 | 增强离线/轨迹 | 离线 UI 在 Hybrid 更完整 |
| 工程填报 | 适合中等表单 | 适合重附件 | 附件队列交互一致 |
| 调度直控 | 通常降级 | 主通道 | 小程序可看数/发起审批，不装假成功 |
| 行政审批 | 很适合 | 可选 | 待办优先 |
| 公众服务 | 主阵地 | 一般不需要 | 极简 IA |

**分轨口诀：对象与状态词一致，深度与摩擦按角色+平台裁剪。**

## 10. 收束

这份报告的终点不是技术选型，而是：

1. **先立全局交互底盘**——布局、List/Card、按钮、数据最小集、轻采集、触达；  
2. **再用五角色的权限与数据视野**裁剪出各自的 UI 哲学与界面模式；  
3. **最后才谈**小程序/Hybrid 如何承载、V2 原子原则如何挂接、还缺哪些规范正文。

**业务附表是因，全局交互是所有角色的共用语法，分角色哲学是语法上的词序与重音——这样 UI 设计才算「由业务决定」。**
